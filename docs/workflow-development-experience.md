> 文档版本：v1.0 ｜ 2026-11-05 ｜ 记录人：DSH 主代理（AI），由人类复核
> 性质：**工程方法与复盘文档**，不是给玩家的文案。所有玩家可见文字仍受 AI 禁用约束，引用处一律标 `PLACEHOLDER` 或注明原话来源。

## 0. 阅读指南

### 0.1 这份文档回答什么

这个项目在 3 周内从一句话灵感做到 311 个自动化测试、37 个测试脚本、可导出构建的完整作品。真正的产出不只是玩法，而是一条**流水线**：

> 人类给出方向与体感 → AI 把体感翻译成可测量的数字 → 规则落在纯逻辑层 → 三道验证门 → 一改一档留痕 → 人类用同一套数字复核。

本文记录这条流水线为什么这样设计、每一环踩过什么坑、以及**下一个项目可以直接照抄什么**。

### 0.2 三种读法

| 读者 | 建议路线 | 预计耗时 |
|---|---|---|
| 新人接手本项目 | §1 → §4 → 附录 B 术语；再读 `docs/dev-contract.md` 与 `docs/dev-example/development-log.md` | 40 分钟 |
| 下一个项目要复用工作流 | §3 十条经验 → §7 模板 → §10 可迁移清单 | 25 分钟 |
| 复盘 / 审计（含 AI 合规审查） | §1.4 量化画像 → §5 案例库 → §8 会话取数方法 → 附录 A 索引 | 60 分钟 |

### 0.3 约定

- **经验**编号 `E01`–`E10`（§3），**案例**编号 `C01`–`C20`（§5）。正文提到经验与案例时只用编号，方便交叉检索。
- 每条事实尽量附**可核对的位置**：文件路径 + 行号、提交号、测试计数、会话消息 ID（`m00525` 这类）。行号写 `文件:行`（如 `project.godot:14`）。
- 区分**事实**与**判断**：带「判断：」「推断：」前缀的是复盘观点，不是当时记录。
- 游戏内帧数一律按 **60Hz 固定逻辑帧**理解：`1f = 16.67ms`。文档中出现「毫秒」时均由此换算。

### 0.4 一句话结论

AI 写游戏最难的不是写代码，而是**让「感觉不对」变成「可复现的失败用例」**。做到这一点，剩下的都是机械工作；做不到，就会陷入「改一版、人类说还是不对」的无底洞。本项目在 10-21 之后基本走出了这个循环，靠的是 §3 的前四条经验。

## 2. 工作流总览

### 2.1 七阶段主循环

| 阶段 | 人类进来什么 | AI 产出什么 | 门禁（不做完不进下一阶段） |
|---|---|---|---|
| ① 立项与契约 | 工作区、截止、活动硬约束 | `AGENTS.md` + `docs/dev-contract.md` + 可执行守卫测试 | 契约里的禁令有对应测试；否则规则只是愿望 |
| ② 策划 | 一句话灵感 + 逐项拍板 | `docs/dev-example/design.md`（玩法、帧表、判定矩阵、里程碑） | 每个 `PLACEHOLDER` 已登记；数值集中在数据资源 |
| ③ 实现 | 方向与手感反馈 | 纯逻辑 → 表现 → UI，小步提交 | 每步跑定向测试；新增 `class_name` 先 `--import` |
| ④ 验证 | 试玩体感 | 探针矩阵 + GUT + headless 冒烟 | 三项都留数字（用例/断言/退出码） |
| ⑤ 评审 | 决定改哪些 | 审计报告（P0–P3）或自审结论 | 只审不改，由人类裁决 |
| ⑥ 留痕 | 拍板结论 | `CHANGELOG.md` + `balance-pass-*.md` + `development-log.md` + `ai-disclosure.md` | 问题 → 修法 → 验证，三段齐全 |
| ⑦ 提交 | 提供 README/封面/文案 | 构建 + 清单核对 | 版本号两处一致；非开发机验证 |

### 2.2 三个反馈闭环（时间尺度不同，别混在一起）

| 闭环 | 周期 | 触发 | 手段 | 失败信号 |
|---|---|---|---|---|
| 数值闭环 | 分钟 | 人类说「太软 / 挡不住」 | headless 机器人探针扫参数矩阵 | 只改数值不看胜率曲线，改完还是不对 |
| 实现闭环 | 小时 | 新功能 / 修 bug | 定向 GUT → 全量 GUT → 冒烟 | 测试数不涨、断言只断言「不崩」 |
| 体验闭环 | 半天–天 | 人类实际试玩或看截图 | 平衡档 + 截图目视 + 设计决策记录 | 改完人类说「感觉没变」，因为改的是像素级参数 |

判断：**三个闭环混用是最大的时间浪费来源**。用体验闭环的手段（反复试玩）去调数值，一轮要几十分钟；用数值闭环的手段（探针）去解决「看不见」，永远调不出来——那属于可见性工程（E06）。

### 2.3 两条并行链：代码链与文档链

```
策划 design.md ──► 实现 ──► 测试 ──► 探针/截图 ──► CHANGELOG 条目
      │                        │              │
      └──── 平衡档 balance-pass-0X.md ◄───────┘
                              │
                        ai-disclosure 一行 + development-log 一节
```

两条链**同一提交**落地。理由很实际：如果代码先提交、文档后补，补文档时已经记不清「为什么改成 14f 而不是 16f」，最后只能写「优化了手感」——这种句子在两周后毫无价值（E04）。

### 2.4 一处反直觉：文档是交付物，不是副产品

本项目的文档量与代码量大致同量级：`design.md` 806 行、`development-log.md` 723 行、`CHANGELOG.md` 489 行、`dev-contract.md` 264 行，另有 4 份平衡档与 2 份试玩记录。它们不是「写给领导看的」，而是**下一轮 AI 会话与人类复核的唯一内存**：

- AI 会话会重启、上下文会压缩，只有仓库里的文档能跨会话传递「为什么」；
- 人类的判断标准会漂移（今天觉得 14f 太慢，明天可能觉得刚好），只有数字化的历史记录能对齐；
- 审计与合规（AI 披露、二次创作声明）本身就是交付物的一部分。

## 3. 十条核心经验

> 每条给：原则 → 为什么 → 怎么做 → 案例 → 判据。案例编号指向 §5。

### E01 把体感翻译成可测量的数字

**原则**：人类说的「太软」「挡不住」「反应不过来」，必须先变成一个可以判定真假的量：帧数、毫秒、胜率、被架次数、可见对比度。做不到这一步，就不算理解需求。

**为什么**：人类无法直接给出帧数，AI 也无法直接理解「软」。中间缺少翻译层时，双方只能在「改一版 → 还是不对」之间循环。项目在 10-20 的两轮平衡里就吃过这个亏（C03）。

**怎么做**：

1. 先问**可感知阈值**，不问具体数值。人类给的「反应极限 0.1 秒、平均 0.2 秒」比任何帧数都好用。
2. 把阈值换算成固定帧：`0.1s = 6f`、`0.2s = 12f`、`0.3s = 18f`。
3. 把「手感」拆成**两个可独立调节的量**：窗口宽度（容错）与提示提前量（可读）。混在一起调，永远调不出结果。
4. 定「变化是否可感知」的门槛：个位数帧数（≤6f）的改动是噪声，时间差别阈限约 10–20%，低于这个幅度的调参不算改。

**案例**：人类在 10-21 说「个位数难度帧数变化不可感知，应按毫秒基准」。这条直接改变了后续所有平衡档的写法——从「前摇 18f → 14f」改写成「前摇 300ms → 233ms」，并在探针里以毫秒档位（帧完美 / 250ms / 350ms）扫描（C03、E05）。

**判据**：一条需求能不能被写成断言或探针指标。写不出，就还没翻译完。

### E02 规则先落在纯逻辑层，表现层只做投影

**原则**：所有判定（前摇、架窗、伤害、心流、AI 决策）放进一个**不继承 Node、不读输入、不依赖场景树**的纯逻辑类；场景与 UI 只读它的状态。

**为什么**：三个消费者要复用同一套规则——对局控制器、GUT 单元测试、headless 机器人探针。规则一旦长在 `Node` 上，探针就得起整个场景，测试就得等物理帧，调参速度会掉一个数量级。

**怎么做**：

```gdscript
class_name DuelSim
extends RefCounted
# 不继承 Node、不读输入、不访问场景树
# tick(): 推进一帧；set_input(action, guard_held): 注入输入
```

- 输入由控制器采集后**注入**（`set_input(action, guard_held)`），模拟层不碰 `Input`；
- 表现层（`DuelView`）每帧只读 `FighterState` 与事件列表；
- 数据与逻辑分离：`FighterData` / `AiProfile` / `SpellCardData` 是资源，数值改资源不改代码。

**案例**：`duel_sim.gd` 同时被 `duel_controller.gd`、`tests/unit/test_duel_sim.gd` 与机器人探针使用。10-21 的手感五连改（C02、C03）全部只改 `duel_sim.gd` 与数据资源，`duel_view.gd` 零改动，因此每轮验证只需 headless 跑探针 + GUT，不需要人类重新试玩。

**判据**：能否在 2 秒内跑完 100 场对局。不能，说明逻辑与场景耦合了。

### E03 三道验证门：探针 → 单元 → 冒烟

**原则**：任何改动的验证必须过三道门，且每道门都留**数字**（不是「通过了」）。

| 门 | 目的 | 命令 / 形态 | 通过标准 |
|---|---|---|---|
| ① 探针矩阵 | 规则是否产生预期胜率/帧数分布 | headless 脚本跑机器人对局，输出 CSV | 指标落在目标区间，且与上一版可比 |
| ② GUT 单元/集成 | 规则边界与信号行为是否被锁住 | `gut_cmdln.gd -gdir=res://tests -gexit` | 用例数/断言数只增不减，退出码 0 |
| ③ 冒烟 | 场景能否起、有无运行时报错 | `--headless --quit-after 240` | 退出码 0，stderr 无 `ERROR` |

**为什么**：单元测试证明「我理解的规则没写错」，探针证明「这条规则在真实对局里产生了预期分布」，冒烟证明「场景没被我改崩」。三者缺一：

- 只有 GUT → 测试全绿但机器人 100% 胜率（C01）；
- 只有探针 → 数值对了但边界没锁，下次改别的又崩；
- 只有冒烟 → 等于没测。

**案例**：10-21 晚的手感五连改，每轮结束都记 `GUT 159/159 → 166/166`，并在平衡档里写探针结果（帧完美 100%、250ms 100/67/100、350ms 33–67%）。11-05 的角色选择轮次记 `311/311、1270 asserts、37 脚本、5.08 s、退出码 0`。

**判据**：新改动的验证记录里，能否同时找到胜率/帧数、用例与断言数、退出码。

### E04 一改一档：文档与代码同一提交

**原则**：每一次影响手感的改动，产出一份固定结构的 `balance-pass-0X.md`；文档和代码进同一个提交。

**为什么**：调参是**多变量**的。没有档案，两周后没人知道「为什么玩家前摇是 14/11/17f 而对手仍是 28–30f」。更重要的是，档案逼你把「诊断」写清楚——诊断写不出来，说明还没定位到根因，只是在试。

**结构模板**（与 `balance-pass-01.md` 一致）：

```markdown
# 平衡调整记录 0X（日期）
> 触发：人类试玩反馈（mXXXXX）——原话要点
## 1. 诊断（含代码位置）
## 2. 改动表（旧 → 新 → 理由）
## 3. 实测（探针矩阵结果 / GUT 计数）
## 4. 遗留风险与未验证项
## 5. 复现命令
```

**案例**：`balance-pass-06-plan.md` 在同一天内迭代到 v3、v4：v3 把「首次格挡后自动反斩」改为「自动架刀 + 反斩、45f 窗口」，v4 又去掉 10f 蓄力改成按 L 瞬发。每次改版都保留旧版本作为历史行，而不是覆盖——因为人类的拍板是逐项发生的（`m00159`、`m00201`）。同一轮里还记录了「方案 §3.2 写 `defender.state != SPELL`，与 45f 内保持 `SPELL` 矛盾」这类**笔误**，供后续读者避坑。

**判据**：一个改动若无法用「旧值 → 新值 → 理由 → 实测」四列写出来，说明它不该被提交。

### E05 用探针矩阵代替人类反复试玩

**原则**：把「人类试玩」换成可重复的机器人矩阵：3 种机器人 × 角色 × 场次 × 随机种子 × 输入延迟档位；输出胜率、平均帧数、被架次数、命中数。

**为什么**：人类一次试玩 10 分钟，只能给一个模糊结论；探针一次跑几百场，能给一条曲线。而且探针不受「今天手感好」影响。

**怎么做**：

```
机器人类型：mash（无脑连砍）/ guard_only（只架不打）/ human（随机延迟 + 读招）
输入延迟档：帧完美 / 250ms(15f) / 350ms(21f)
变量：角色（均衡/快剑/重剑）× 场次（0/2/4）× seed（多个）
指标：胜率 / 平均决斗帧数 / 被架次数 / 命中次数 / 空架次数
```

**关键细节**：

- 探针必须跑在 **NORMAL 难度档**（`HARD` 回滚旧帧数，会污染结论）；
- 统计量放 `Dictionary`：GDScript lambda **按值捕获**局部变量，累加器用局部变量会永远为 0；
- 探针脚本放 `.tmp_probe/`，跑完即删，不进仓库——否则它会变成第二套需要维护的测试。

**案例**：C01 里「连砍机器人胜率 100%」第一次暴露时，团队以为是数值问题（伤害太高/架窗太窄），连改两轮数值无效；探针把「AI 从不架招」这个状态机问题暴露出来后，修复只改了一个清零条件，胜率立刻落到 67/33–67/67，再修一次到 NORMAL 档对均衡/快剑 0%、重剑仍 67–100%。

**判据**：改数值后能否在 5 分钟内给出「对哪类玩家、在哪个延迟档、胜率多少」。

### E06 可见性工程：规则的每个优势都要能被看见

**原则**：规则上的一个「优势」，如果没有对应的视觉（或听觉）差异，对玩家就等于不存在。改规则前先问：玩家靠什么看出来？

**为什么**：本项目没有配音、没有正式音效，玩家唯一的信息通道是画面。团队多次把「机制已经生效」误当成「玩家能感知」。

**怎么做**：把每个机制拆成「状态 → 可见信号 → 阈值」三列，逐条填。填不出的，要么补表现，要么删机制。

**案例**：

1. **看破失效**：U05「看破」的 `hint_lead = 6`（提前 6f 看到收束环）是唯一的优势，但 `_update_charge_fx()` 在 `imminent`（临刀 8f 内）把整环**硬切**成纯金——起手、中段、临刀三阶段颜色几乎一样，6f 提前量被抹平。修法是抽出 `charge_color(progress, imminent, pulse)`，让颜色沿 `smoothstep(0.12,1.0,p)` 从近白过渡到金，临刀只做 0.7 的 lerp 与 alpha 呼吸，再给带 `hint_lead` 的一方加一段环外冷白预读弧，并重拍截图目视。
2. **无音效判断困难**（人类 10-20 反馈）：给 `COMMIT` 加头顶「气」环（半径 58→74、alpha 0.15→0.65，进度 > 70% 加一颗亮点）。这是纯视觉提示，不改判定——这条边界很重要，否则会变成「用表现改平衡」。
3. **残心显示**：人类要求删掉「残心」显示以降低入门门槛。诊断发现残心的唯一 HUD 写入点在 `duel_hud.gd` 的 `_refresh_body()`，与规则层解耦（残心对数值的影响在 `scripts/run/run_state.gd` 的 `player_data()` 里）——删显示零机制风险。后来人类又要求结算页也不要保留小字，测试改成 `test_zanshin_is_hidden_everywhere_in_hud`：用 `find_children` 扫 HUD 全部可见 Label，断言不含「残心」，同时断言 `run.zanshin` 仍为 2（机制照常记数）。**表现删除不等于机制删除**，测试要同时锁两头。
4. **L 键没提示**：`_controls_text()`（`duel_hud.gd:290`）当时只替换 attack/guard/restart/pause，没有 spell；操作行文案也没有符卡位。规则早就有了，玩家不知道——这就是可见性缺口。后来补齐：`localization/zh_CN.json:9-11` 的三条操作行已含 `%s` 符卡位（`controls` / `controls_template` / `controls_versus_template`），核对方式是在语言文件里搜这三条 key。

**判据**：拿一张静帧截图，能否说出「这一帧比对手多拥有了什么」。说不出，就是没做可见性。

### E07 表现层「先量再摆」：几何先量，参数先验量级

**原则**：贴图/特效的摆位，先量测贴图本身的几何（亮带半径、张角、不透明度峰值），再用「目标值 / 贴图值」算缩放；shader 看起来没变化时，先检查参数与几何的**量级关系**，不要先怀疑混合模式。

**为什么**：美术反馈是「感觉不对」，但不对的原因往往是像素级的：月牙亮带在 512 贴图的 203 半径处、符卡环外缘在 172/512 处、粒子贴图是 512 见方而角色只有 46×150。凭直觉给 `scale = 0.5` 一定错。

**怎么做**：

1. 用脚本统计「alpha > 阈值」像素的极坐标分布，得到亮带半径与张角（本项目用 System.Drawing 跑了一次性统计）；
2. 缩放系数 = 目标半径 / 贴图亮带半径（不是 / 256）；
3. 旋转量 = 贴图中心角取反；P2 再加 180°；
4. shader 参数先换算成「占几何的比例」再给值；
5. 截图前**停掉状态机驱动**（`set_process(false)` / `set_physics_process(false)`），否则下一帧就被 `_update_*_fx()` 收走。

**案例**：

- 刀光 `twirl_03`：极坐标统计得亮带 **175–231 / 512**（中位 203）、张角 **-80°…+28°**（中心 -26°、跨度 108°），旧弧是 ±51.5°、半径 122。于是缩放 `122/203 ≈ 0.60`、旋转 `+26°`，月牙正好压住旧弧。后来人类要求「离刀身远一些」，把 `SLASH_RADIUS` 提到 136，亮带落到 117–155，离刀身约 14px。
- 扇形消失 shader：首版 `tail_span = 1.35`（77°）比月牙总张角 108° 还宽，等于永远不塌陷，肉眼只看到整体淡出。三格裁切 + 亮像素统计（1079/3093/2663/318）后收到 `0.16`（9°）才出现「上端消失 → 半截 → 收尾」（C06）。
- 雨线：把 `width` 当像素用，`step(remainder * amount, width)` 在整格内恒为 1，屏幕成了竖条纹。正解是先算格内中心距 `center_dist = abs(remainder / cell - 0.5) * 2`，再 `slim = 1 - smoothstep(0, width, center_dist)`（C07）。
- 粒子：对刀特效 26 颗 / 190px 叠成纯白 → 10 颗 / 150px → 7 颗 / 140px；加法混合下观感强度近似「数量 × 单颗尺寸」的平方效应（C04）。

**判据**：每个几何参数都能写成一条除法或比例式，而不是「试出来的」。

### E08 契约化：约定不会被执行，只有测试会

**原则**：任何「团队约定」都必须有对应的可执行检查，否则它会在第一次赶工时被绕过。

**为什么**（这是本项目最重要的一次教训）：10-21 审计发现，项目引入了 **33 个 GDAS 技能，实际加载 0 次**；`EventBus` / `UIManager` / `Codec` 三个框架插件**零调用**。根因不是 AI 懒，而是 `AGENTS.md` §9 只写了「实现前先按任务匹配加载技能」这句**背景说明**，没有强制门、没有验收项、也没有测试能发现违规。

**怎么做**：把约定升级为 `docs/dev-contract.md`，四层结构：

| 层 | 内容 | 可执行性 |
|---|---|---|
| 开工清单（§1） | 读契约 → 声明本次加载的技能与插件 → 真加载 → 完成后跑 GUT → 提交前过验收 | 声明缺失可被人类一眼发现 |
| 映射表（§2） | 任务 → 必载技能（如「战斗判定」→ combat-system + 2d-physics + genre-fighting） | 消除「不知道加载哪个」的借口 |
| 禁令（§3/§3.1） | 禁用直读输入、禁用自建音频播放器、禁用 TranslationServer……**豁免必须登记** | `tests/unit/test_project_contract.gd` 扫描 `res://scripts/` 全部 `.gd` |
| 验收（§5） | 9 条提交前检查：技能已加载、无新增直读、GUT 全绿、docs 已更新、ai-disclosure 已追加、无 AI 生成内容…… | 每条都有对应文件或命令 |

**守卫实现的关键细节**（`test_project_contract.gd`）：

- 扫描前**剥离注释与字符串字面量**，否则文档里的示例代码会误报；
- 扫到的脚本数异常少（比如路径写错）也直接失败，防止「因为没扫到所以全绿」；
- 禁止项包括 `Input.is_action_*`、`Input.get_axis(`、`AudioStreamPlayer*.new(`、`TranslationServer.`、`GUIDEMappingContext.new(`、`AudioServer.set_bus_volume_db(`、`InputMap.action_add_event(`、`GUIDE._input_state`、`config._bind(` 等；
- 新增禁止项的顺序固定：**先改 §4 文档 → 再加 `_BANNED` → 再修代码**，避免「规则先于文档」的漂移；
- 真实需要破例的 5 处（Master 音量、内置 `ui_*` 手柄动作、GUIDE 热插拔刷新、`GUIDERemappingConfig._bind/_unbind`、`Input.get_connected_joypads()`）逐条登记，**限定文件范围**，而不是关掉检查。

**案例**：插件从「接线」到「替换实现」走了三轮——第一轮只是让代码调用 `Codec`/`UIManager`；第二轮发现「有个壳但行为还是自己的」，改成 `Codec.record` / `AnyCodec`、`UIManager` 补 autoload 并改用 `UIPanel` 栈、`EventBus` 事件刷新；第三轮把 GUIDE 上下文**资源化**，删掉约 300 行运行时现搭代码。技能侧也在第二轮才真正被加载（`skill` 12 次调用集中在 3 个会话）。

**判据**：契约里的每一条禁令，能否在测试文件里指到对应字符串。指不到，就是愿望。

### E09 合规内建：把「不能做什么」写进文件与流程

**原则**：活动硬约束（AI 不得生成美术/音乐/文案）不是收尾检查项，而是**从第一次提交起就生效**的工程约束。

**为什么**：截止前补合规几乎必然出事——文案已经写进 UI、占位符散落在 `.tscn` 里、没人记得哪句是 AI 写的。本项目把合规拆成四件可执行的事：

1. **命名**：所有玩家可见文字以 `PLACEHOLDER` / `PH_` 标记，自动可搜；
2. **登记**：`docs/gamejam/placeholder-inventory.md` 与 `docs/gamejam/44 条本地化占位.md` 逐条列负责人；
3. **披露**：`docs/gamejam/ai-disclosure.md` 每个模块完成后**即时**追加一行（日期 / 模块 / AI 产品 / 用途 / AI 率 / 人类复核），不攒到截止前补写；
4. **声明**：游戏内「关于」页与提交 README 必须写二次创作声明，且禁止暗示官方授权。

**AI 率口径**（便于审查）：100% = 整个文件由 AI 首生成；50–90% = AI 打底、人类结构性修改；<50% = 人类主导；0% = 纯人工。艺术资产一律 0%（因为禁止），只在声明区写一次。

**案例**：本轮工作流文档本身也按同一规则登记——文档属「工程内部文档，非作品内容」，AI 率 100%，人类复核待定。符卡与教程文案则全部留空，等人类写。

**判据**：提交前能否在 1 分钟内列出所有占位符与它们的人类负责人。

### E10 环境铁律：工具链的坑必须写进文档

**原则**：同一台机器、同一套工具，坑会重复出现。踩过一次就写进 `development-log.md` §0，下次直接照做。

**三条硬规则（本项目血泪）**：

| 场景 | 错误做法 | 正确做法 | 后果 |
|---|---|---|---|
| 改 UTF-8 源码 | PowerShell `Set-Content` / `-replace` 写回 | 只用 `edit` / `write` | 写入非法 UTF-8，`read` 报 `invalid UTF-8 text`，只能 `git checkout` 恢复 |
| 抓 Godot 输出 | `godot ... | Select-Object` | `Start-Process -RedirectStandardOutput` 再读文件 | 管道拿不到 stdout，`$LASTEXITCODE` 不可靠；`| Select-Object` 还会把退出码变成 1 |
| 新增 `class_name` | 直接跑测试 | 先 `--headless --import` | `global_script_class_cache.cfg` 未更新，报 `Nonexistent function 'new' in base 'GDScript'` |

**另外四条反复出现的坑**：

- `.gitignore` ≠ Godot 不导入：`temp_assets/` 需额外放 `.gdignore`，Godot 才整目录跳过；验证方式是反查「未选中文件在 `.godot/imported/` 里没有 `.ctex`」（C18）。
- `assert_no_new_orphans()` 不能放在 `after_all`：GUT 的孤儿计数器只在当前测试有效，会报 `Nonexistent function 'size' in base 'Nil' addons/gut/test.gd:2085`（C19）。
- 截图工具必须停掉状态机驱动：`view.set_process(false)`、`scene.set_physics_process(false)`、`set("_flash", 0.0)`，否则手动摆的位置下一帧就被收走（C16）。
- `edit` 的 `old_string` 含行尾续行反斜杠时，JS 模板字符串会吞换行导致失配；含续行一律用 `String.raw`（C15）。

**判据**：同一类错误是否在 `development-log.md` 里出现第二次。出现第二次，说明铁律没写或没读。

## 4. 分阶段操作手册

> 本章把 §3 的十条经验落到「每个阶段具体做什么」。每节固定四行：**输入**（开始前必须有）、**动作**（AI 做什么）、**产出**（写进哪个文件）、**门禁**（不过不许进下一阶段）。案例编号指向 §5。

### 4.1 阶段 0：立项与契约（半天）

**输入**：活动参与指南、二次创作规约、GitHub 仓库地址、目标引擎版本。

**动作**：

1. 把活动硬约束抄成独立文件（`docs/gamejam/constraints.md`），不要只留在聊天里。硬约束是**可被违反的**，聊天记录不会在三个月后提醒你。
2. 写 `AGENTS.md`，但**只写背景说明是不够的**（E08 教训）。真正的门禁是 `docs/dev-contract.md`：开工清单、任务→技能映射、插件禁令、可执行守卫、验收 9 条。
3. 第一次提交就把「占位符规则」「AI 披露规则」写进契约，而不是等有文案了再说。
4. 建 `.tmp_probe/`、`temp_assets/` 这类**工作区外的临时目录**并在 `.gitignore` 里排除；临时目录要有清理责任人和清理时点。

**门禁**：让一个陌生 AI 会话只读 `AGENTS.md` 与 `dev-contract.md`，能否正确说出「我不能做什么」和「我必须跑什么命令」。

**失败案例**：本项目第一版 `AGENTS.md` §9 写的是「使用约定」——「实现前先按任务匹配加载对应技能」。语气是建议，没有验收项。结果 33 个技能在两天里加载 **0 次**，直到人类 U23 直接质疑「确认开发并没有通过项目技能辅助」才暴露。

### 4.2 阶段 1：策划（半天到一天）

**输入**：一句灵感（本项目：「剑术（居合道）与心流——东方 Project 各角色间的瞬息间剑术对决」）+ 主题「心」。

**动作**：

1. **不要一次写 800 行**。先用 `ask_user_question` 分批确认（本项目 6 次提问）：单机还是对战、5 场阶梯还是无限、存档要什么、失败条件、美术从哪来。
2. 写**四条设计支柱**，每条必须是可判定的取舍标准。本项目的四条：

   | 支柱 | 含义 | 它否决了什么 |
   |---|---|---|
   | 静—动—余 | 每一刀有蓄力（静）、出刀（动）、收势/残心（余） | 否决了「按住连砍」的流畅型手感 |
   | 输在贪不在手慢 | 输因是判断错误，不是手速不够 | 否决了 QTE、否决了需要 0.1s 反应的窗口 |
   | 心流是看得更清 | 心流值换的是信息与选择，不是伤害倍率 | 否决了「心流越高伤害越高」 |
   | 每一刀都可归因 | 玩家能说出这一刀为什么中/被架 | 否决了随机暴击、否决了隐藏读招 |

3. 帧表按 **60Hz 逻辑帧 + 毫秒双写**（如 `前摇 18f / 300ms`），并在文档开头写明「这是 vX.Y 的快照，有效值以代码为准」。
4. 先写**失败条件**与**不做清单**：本项目明确「无背景 Demo 优先」「不用原作素材」「文案全部占位」。
5. 设计文档里每个数值都要能被 `fighter_data.gd` 反向对上，否则就是文档债。

**门禁**：拿设计文档问任何一个没参与的人「这个游戏输赢由什么决定」，他能在 30 秒内答出，且答案与代码一致。

**失败案例**：`design.md` 的 §6.3 帧表在 v0.14 之后就没同步过，代码已经改成 14/11/17f，文档还是 18/15/21f。后来在开头加了一段「本文档已被 0.1.0 取代」的声明才止血——正确做法是**每次改数值顺手改文档**（E04 的文档与代码同提交）。

### 4.3 阶段 2：实现（一到两天，灰盒优先）

**输入**：design.md 的四条支柱与帧表。

**动作（严格按顺序）**：

1. **纯逻辑先行**：`class_name DuelSim extends RefCounted`，不接受输入设备、不继承 Node、不 preload 场景。所有判定在 `_step()` 里推进，输入通过 `set_input(action, guard_held)` 注入。这样同一份逻辑能同时被：控制器（真人）、`DuelAI`（机器人）、GUT（测试）三种消费者使用（E02）。
2. **场景只做展示**：`duel_view.gd` 读状态画，不写规则。画的时候注意「命中当帧转 RECOVERY」这类坑（E06 的刀光渲染问题就是从这来的）。
3. **输入一律 GUIDE 上下文资源**：`input/actions/*.tres` + `input/contexts/*.tres` 用 `tools/generate_guide_context.gd` 生成；代码里禁止 `GUIDEMappingContext.new()`。需要新键位改 `KeyBindings` 再重跑生成器。
4. **UI 走 UIManager 面板栈**，音频走 `SoundManager`，本地化走 `I18NManager`，数据表走 `RegistryManager`，存档走 `Codec`——这是 E08 的「插件优先」在实现阶段的落地。
5. **每个模块完成即跑 GUT**，不要攒到最后。新增 `class_name` 后先 `--headless --import` 再跑测试（E10）。
6. **临时脚本放 `.tmp_probe/`**，跑完删除；提交前 `git status` 里不应出现它们。

**门禁**：三个消费者（真人、机器人、测试）都能驱动同一份逻辑，且结果可复现（固定 `seed`）。

**失败案例**：本项目有过一次「在 `duel_controller.gd` 里直接 `Input.is_action_just_pressed`」的写法，被守卫测试拦下。修法不是加豁免，而是把读取挪到 `scripts/core/input_guide.gd` 并包一层。**禁令的目的是把输入集中到一处**，而不是禁止输入。

### 4.4 阶段 3：验证（每次改动后，10 分钟到 1 小时）

**三道门，缺一不可**（E03）：

| 门 | 命令 / 形态 | 耗时 | 通过标准 | 它抓什么 |
|---|---|---|---|---|
| ① 探针 | `pwsh -File .tmp_probe/probe_matrix.ps1`（自建） | 5–30 秒 | 机器人胜率落在预期区间 | 规则级回归（数值、AI 行为、死循环） |
| ② 单元 | `godot --headless --path . -s addons/gut/gut_cmdln.gd -gdir=res://tests -ginclude_subdirs -gexit` | 20–60 秒 | 退出码 0 且输出 `All tests passed!` | 逻辑与契约（含 `test_project_contract.gd`） |
| ③ 冒烟 | `godot --headless --path . --quit-after 240` | 10–20 秒 | 无 `ERROR`/`SCRIPT ERROR`，退出码 0 | 场景装配、autoload、资源加载 |

**读输出的技巧**：

- 必须用 `Start-Process -RedirectStandardOutput` 落盘再读，管道拿不到 Godot 的 stdout（E10）；
- 不要把 `godot ... | Select-Object -Last 5` 写进判断，`Select-Object` 会把 `$LASTEXITCODE` 变成 1，造成「明明过了却失败」（C12）；
- GUT 的通过标志是 `All tests passed!`，不是退出码为 0 就万事大吉；
- 断言计数要记进 commit message 或 CHANGELOG（311 用例 / 1270 asserts / 37 脚本），数字变小就是删了测试。

**失败案例**：平衡 02 只跑了 GUT（67/67 全绿）就宣布「连砍问题已修」，结果机器人探针一跑，连砍胜率仍是 100%——因为 GUT 里没有「AI 一挨打就再也不架」这条状态机路径。**GUT 通过 ≠ 玩起来对**，这正是门 ① 存在的理由（C01）。

### 4.5 阶段 4：手感与平衡迭代（本项目的主战场）

**输入**：人类的一句体感（「防御窗口太小」「用符卡没什么感觉」）+ 一个可复现场景。

**动作（五步，顺序不可换）**：

1. **分级**：先判断反馈属于哪一层（§2.2）。帧数/伤害 → 数值层（分钟级）；「按了没反应」→ 输入/状态层（小时级）；「看起来不对」→ 表现层（半天级）。**分级错了会白改**。
2. **量化**：把体感翻译成数字并写进文档。例：人类说「反应极限 0.1 秒」，换算 `0.1s × 60Hz = 6f`；说「平均能反应 0.2 秒」，就是 `12f` 的前摇才是「可被人类的读招窗口」。
3. **定位**：用探针复现，拿到基线数字。**没有基线不放改动**。基线要包含：胜率、平均帧数、被架次数、命中数（E05）。
4. **最小改动**：一次只动一个变量组，且**先改可读性再改数值**。本项目多次证明：看起来是数值问题，实际是状态机问题（C01 的 AI 读招粘滞、C03 的 GUARD 无 ATTACK 分支）。
5. **同提交留痕**：`balance-pass-0X.md` 与代码同一 commit（E04）；文件里写清「触发（含人类消息编号）→ 诊断（含 `文件:行`）→ 改动表（旧/新/为什么）→ 实测表 → 遗留风险 → 复现命令」。

**门禁**：把 balance-pass 交给没参与的人，他能照着复现命令得到同样的数字。

**失败案例**：平衡 04b 之前，团队试了三种输入缓冲方案（无缓冲 / 4f 缓冲 / 8f 缓冲），每次都用探针验证「操作成功率」——都通过了。但人类复测说「缓冲反而导致操作迟缓」。结论：**读招类对局里，确定感 > 容错**，于是彻底删掉缓冲（`buffer_action`/`buffer_expire_frame`/`_consume_buffered_input` 等）。这个结论不是测出来的，是**测 + 人**一起得出的——所以 E01 才要求「人类验收标准也必须是数字」（这里就是「按下去 0 帧延迟出刀」）。

### 4.6 阶段 5：表现与素材接入（半天到一天，最容易被低估）

**输入**：人类提供的素材包 / 明确的观感描述。

**动作**：

1. **先量再摆**（E07）：统计贴图亮带半径、张角、alpha 峰值，再算缩放与旋转。
2. **素材暂存区双保险**：`temp_assets/` 同时进 `.gitignore` 和放 `.gdignore`（Godot 才会整目录跳过）；验证方式是反查 `.godot/imported/` 里没有对应 `.ctex`。
3. **一张贴图承担一个语义**：不要把同张贴图叠两枚再调，先怀疑语义重复（C08 的 circle_02 事件）。
4. **替换而不是叠加**：启用新表现时删掉旧的 `_draw_*` 代码，否则两套表现会打架（C09 的蓄力环）。
5. **用截图闭环**：写 `tools/capture_*.gd` 一次性截图脚本，三轮迭代内收敛；截图前必须停掉状态机驱动（`set_process(false)`、`set_physics_process(false)`、`set("_flash", 0.0)`）。
6. **颜色策略**：攻击方制（命中 = 出刀方颜色，架住 = 防守方颜色），刀光保持白色不吃方色；加法混合下「数量 × 单颗尺寸」是平方关系（C04）。

**门禁**：把截图给人类看，人类说「就是这个感觉」——而不是你自己觉得对。

**失败案例**：蓄力环第一版用 `star_03`，`maxAlpha` 只有 73，怎么调都不亮；换 `light_03`（235）后一次通过。**素材本身的上限决定了调参空间**，先量素材再调参（C10）。

### 4.7 阶段 6：评审与审计（半天，按需）

**输入**：明确的审计范围（全量 / 仅 `res://scripts/` / 只看某模块）。

**动作**：

1. 用**只读子代理**并行审（本项目 6 个子代理：架构、契约、测试、性能、文档、素材）。子代理只读，产出报告，不改代码。

4. 修复批次化：每批一个主题（如「输入链路」「存档编解码」「文档漂移」），每批跑 GUT 并记录计数变化。

**门禁**：P0/P1 全部关闭，且每一条修复都能指到测试或用例。

**失败案例**：第一轮插件「接线」完成后，审计发现三个插件虽然被调用，但行为还是原来的实现——这叫「有个壳」。修法是**替换实现**而不是调用 API（E08 第三轮）。

## 5. 案例库（C01–C20）

> 每个案例给出：**场景 → 症状 → 根因 → 处理 → 结果 → 可迁移结论**。数字与路径保留原始精度，便于复核。案例全部来自本项目真实提交、文档或会话记录。

### C01 「无脑连砍」看起来是数值问题，实际是状态机问题

- **场景**：平衡 02 之后，探针里「连砍机器人」胜率仍是 100%，人类反馈也是「能连续出刀瞬间结束战斗」。
- **症状**：所有数值都调过了（前摇 18–20f → 28–30f、架窗 18–22f、HP 3–4 → 30/30/40、伤害 1/2 → 10/7/15），仍然一边倒。
- **根因**：`DuelAI` 的读招骰子 `_guard_planned` 只在 AI 处于 `IDLE` 时清零。玩家连续出刀时 AI 永远不在 IDLE，于是「读招结果」被永久粘滞——要么永远架、要么永远不架。表现是「无脑连砍无敌」，实际是 AI 根本没重新决策。
- **处理**：在「`me.state != IDLE` 就早退」之前，按「对手是否仍在构（蓄力）」提前清零 `_guard_planned`，让 AI 在对手收势时立刻重掷。
- **结果**：连砍机器人胜率 100% → 67/33–67/67；NORMAL 档对均衡/快剑降到 0%，对重剑仍 67–100%（符合「重剑不能靠贪刀赢」的支柱）。
- **结论**：**探针只能告诉你「一边倒」，不能告诉你「哪一层」**。看到胜率异常，先问「AI 的决策状态有没有被重置」，再问数值。

### C02 守卫窗口公式：把「能挡住」翻译成一个区间

- **场景**：人类反馈「防御窗口太小，几乎没法架」。
- **症状**：架防（guard）窗口参数改了三次都没找到手感，且不同敌人手感差异巨大。
- **根因**：没有把「窗口」写成几何关系，而是逐个敌人试。真实关系是：敌方前摇 `T`、玩家架窗 `G`，能挡住的那一帧区间是 `[T − G + 1, T − 2]`；上界由「1f 输入延迟 + 1f guard_startup」决定，与 `G` 无关。
- **处理**：先按公式求出「要挡住 T=18–20f 的敌人，至少需要 `G = ` 多大」，发现当时 T 太小才是根因。于是敌方前摇 18–20f → 28–30f（467–500ms），玩家架窗 12–20f → 18–22f。
- **结果**：250ms 档帧完美反击 100/67/100，350ms 档降到 33–67%，形成「越快越难」的曲线（而不是「越快越好挡」的倒挂）。
- **结论**：**窗口类手感问题，先写出不等式，再改参数**。公式同时解释了「为什么加长窗口没用」——瓶颈在上界 `T−2`。

### C03 GUARD 状态没有 ATTACK 分支

- **场景**：人类反馈「架住之后反击很别扭，要等硬直结束才能出刀」。
- **症状**：架防成功后按攻击键经常没反应；偶尔又能出刀，看起来像「随机吞键」。
- **根因**：状态机 `GUARD` 分支里只有 `GUARD → IDLE`，输入处理落在 `_: pass` 里被吞掉；同时「构 → 架」的取消窗只有 5f，比收架硬直 7–9f 还短，等于取消永远不生效。
- **处理**：取消窗 5f → 10f；`GUARD` 中按斩立即出刀（走架后反击分支，前摇 −6f）；架住后给 30f 反击窗。
- **结果**：探针帧完美反击 100%，250ms 100/67/100，350ms 33–67%；「吞键」投诉消失。
- **结论**：**「随机吞键」几乎总是状态机分支缺失，不是输入设备问题**。诊断方法是把所有状态的输入分支列成矩阵，空格子就是吞键点。

### C04 对刀粒子：从一颗纯白球到三个层次

- **场景**：第一次接入对刀（clash）特效，截图是一团纯白。
- **症状**：26 颗 `impact_*` 贴图、190px 尺寸，加法混合下完全过曝，看不到贴图形状。
- **根因**：加法混合的观感强度近似「数量 × 单颗尺寸」的**平方效应**；26 颗 190px 叠在一起，单颗形状必然被吃掉。
- **处理**：三轮收敛：26 颗/190px → 10 颗/150px → 7 颗/140px，初速 320–700，并对齐「攻击方制」上色。
- **结果**：能看出「中心冲击 + 外圈火花」两层结构；GUT 仍全绿（`capture_fx_preview.gd` 截图脚本不参与测试）。
- **结论**：**加法混合先降数量再降尺寸**，并且一次只改一个维度，否则第二轮无法归因。

### C05 刀光贴图：用除法代替「手感调参」

- **场景**：把程序绘制的弧线换成正版 `twirl_03` 刀光贴图。
- **症状**：直接 `scale = 0.5` 后月牙要么缩在刀身里，要么糊到屏幕外。
- **根因**：贴图的亮带不在贴图中心，而在 512 见方中的半径 **175–231**（中位 203）处，张角 **-80°…+28°**（中心 -26°、跨度 108°）。用 `/256` 猜缩放必然错。
- **处理**：先跑一次性统计（alpha > 96 的像素极坐标直方图），得缩放 `122/203 ≈ 0.60`、旋转 `+26°`（P2 再加 180°），弧心复用 `_swing_center()`；挥砍的 4–6 帧连续态改用 `Sprite2D` 每帧 `pose_slash()`，不启动粒子。
- **结果**：月牙精确压住旧弧；后续人类要求「离刀身远一点」时，只改 `SLASH_RADIUS` 122 → 136 一个数。
- **结论**：**几何参数写成除法，就只需要改一个数**；写成「试出来的」，每次改动都要重试。

### C06 扇形消失 shader：参数比几何还宽时永远不会塌陷

- **场景**：给刀光加「上端先消失」的裁剪 shader（`slash_sweep.gdshader`）。
- **症状**：打开 shader 后整片刀光只是整体变淡，看不到「上端消失 → 半截 → 收尾」的过程。
- **根因**：首版 `tail_span = 1.35` 弧度（约 77°），而月牙总张角只有 108°、单侧约 54°——裁剪窗口比几何还宽，等于裁了个寂寞。亮像素统计（裁剪后剩余亮像素 1079/3093/2663/318）证明三格几乎一样。
- **处理**：`tail_span` 1.35 → 0.16 弧度（约 9°），并把旋转量按贴图中心角补偿。
- **结果**：三格出现明确的「消失 → 半截 → 收尾」层次。
- **结论**：**shader 参数要先换算成占几何的比例**（9° / 54° ≈ 17%），再看效果；参数大于几何范围时，效果恒等于无。

### C07 雨丝 shader：把宽度当像素用，整屏变竖条纹

- **场景**：给雨夜背景写 `` 里第二层雨丝（`rain_night.gdshader` 的远雨/近雨）。
- **症状**：打开后屏幕出现均匀竖条纹，完全没有雨丝的「细长、稀疏、随机」感。
- **根因**：`step(remainder * amount, width)` 里的 `remainder` 是「格内归一化坐标 × amount」的结果，值域远大于 `width`，整个格子内几乎恒为 1，于是每一格都被填满成条纹。此外 `fbm` 只用 4 octave 且没有做时间偏移，雨雾像静态噪点。
- **处理**：先算格内中心距 `center_dist = abs(remainder / cell - 0.5) * 2`（0 在格中心、1 在格边），再 `slim = 1 - smoothstep(0, width, center_dist)`，让雨丝在格中心最实；雨速改为多层不同速率。
- **结果**：出现远近两层、方向一致的斜向雨丝；`edge_darkness = 0.94` 的暗角让画面沉下去。
- **结论**：**shader 里凡出现「看起来像整块」的东西，先怀疑某个值域没归一化**。诊断手法：把 `step` 的输入 `clamp` 到 0–1 后 `print` 一次。

### C08 贴图身份疑云：circle_02 看起来像 circle_03

- **场景**：符卡爆环用 `circle_02`，人类质疑「为什么看着像 circle_03」。
- **症状**：肉眼判断像另一张贴图，团队一度准备换图。
- **根因**：贴图身份没错（MD5 `8634C6D0…`、43,380 B，确为 circle_02），错的是**用法**——同一贴图在同一位置叠了两枚（内环 + 外环）并加法混合，外缘亮带被读成「厚环」，看起来就像另一张更粗的贴图。
- **处理**：删掉内环，只留外缘；缩放 = 目标半径 / 172（贴图外缘半径），内外 0.72 倍，半径 36 → 366 ease-out，0.62s，alpha `(1−t)^1.4 × 0.75`。
- **结果**：恢复成单环扩散。
- **结论**：**贴图身份正确 ≠ 观感正确**。遇到「像另一张图」，先查「有没有叠两枚」，再查贴图本身。

### C09 蓄力环：替换不是叠加

- **场景**：把蓄力（charge）提示从程序绘制改成贴图环。
- **症状**：新环看着「脏」，出现双环同心。
- **根因**：新贴图加上了，但旧的两道 `draw_arc` 还在 `_draw_fighter()` 里——两套表现叠加。
- **处理**：删掉旧 `draw_arc`；尺寸 96 → 20 起步、放大到 132（人类指正后改的，不是我原本的 96），颜色 `#fffdf7` → `#ffc94a`，圆心改到 `(x, GROUND_Y − 90)` 与心流环同心。
- **结果**：单环、由白转金、与心流环同心，符合人类「从小到大、由白转金」的描述。
- **结论**：**接入新表现的同一提交里，必须删掉旧表现**；否则「新 bug」其实是「旧代码没删」。

### C10 素材上限决定调参空间：star_03 的 maxAlpha 只有 73

- **场景**：蓄力环试了 5 张候选贴图（`magic_02`、`magic_03`、`circle_02+05`、`star_03`、`light_03`）。
- **症状**：用 `star_03` 时怎么调 color/energy 都不亮。
- **根因**：`star_03` 的 alpha 峰值只有 73（/255），而 `light_03` 是 235。加法混合下，贴图自身峰值决定了亮度天花板。
- **处理**：先量每张候选的 `maxAlpha`，再选 `light_03`。
- **结果**：一次通过。
- **结论**：**先量素材，再调参数**。素材峰值不够时，调参只是在跟天花板较劲。

### C11 输入缓冲三方案：机制对，手感错

- **场景**：人类 10-21 反问「有输入缓冲吗」，随后又说「缓冲反而导致操作迟缓，取消更合适」。
- **症状**：三种方案（无缓冲 / 4f 缓冲 / 8f 缓冲）在探针里「操作成功率」都合格，但真人复测一致觉得慢。
- **根因**：探针测的是「能不能出招」，不是「按下去到出刀的延迟」。缓冲把「按键 → 生效」从 0 帧变成「最多 N 帧后生效」，而这是读招类对局里最敏感的延迟。
- **处理**：彻底删除 `buffer_action()` / `buffer_expire_frame` / `spell_buffer_expire_frame` / `input_buffer` 与 `_buffer`/`_buffer_next_attack`/`_consume_buffered_input`；输入要么当场生效要么当场作废。
- **结果**：GUT 从 159 增至 166 用例（删缓冲后补了延迟断言）；人类复测「跟手了」。
- **结论**：**当机制指标与体感冲突时，先检查「指标测的是不是同一件事」**。本项目最终结论：读招类对局里「确定感 > 容错」（E-INPUT 决策，见 `docs/dev-example/balance-pass-04.md`）。

### C12 退出码陷阱：Select-Object 把成功变成失败

- **场景**：用 pwsh 跑 GUT 并判断结果。
- **症状**：测试明明全过（输出 `All tests passed!`），脚本却报失败。
- **根因**：`godot ... | Select-Object -Last 5` 会让 pwsh 认为管道末端是 `Select-Object`，`$LASTEXITCODE` 变成 1；同时管道本身也拿不到完整 stdout。
- **处理**：改成 `Start-Process -FilePath godot -ArgumentList ... -RedirectStandardOutput out.txt -NoNewWindow -Wait`，再 `Get-Content out.txt | Select-String 'Tests|Asserts|All tests'`；判定以文本标志为准。
- **结果**：CI 与本地判定一致。
- **结论**：**外部进程的「结果」只看两样：明确文本标志 + 落盘输出**。不要依赖管道后的退出码。

### C13 PowerShell 写源码写坏 UTF-8

- **场景**：用 pwsh 批量替换 GDScript 里的字符串（想快一点）。
- **症状**：替换后 `read` 报 `invalid UTF-8 text`，Godot 解析失败；后续所有基于该文件的编辑都失败。
- **根因**：PowerShell 5.1 的 `Set-Content` / `-replace` 默认按系统 ANSI 代码页写回，中文注释被写成非法字节序列。
- **处理**：`git checkout` 恢复；此后所有源码改动只用 `edit` / `write`；把这条写进 `development-log.md` §0 与 `AGENTS.md`。
- **结果**：同类事故未再发生（截至 11-05）。
- **结论**：**文本编辑工具的选择是工程决策，不是个人偏好**。任何会改变文件编码的批量脚本都必须先用一个临时文件验证再上源码。

### C14 新增 class_name 后没 import：Nonexistent function 'new'

- **场景**：新建 `spell_a.gd`（含 `class_name SpellA`）后直接跑 GUT。
- **症状**：`Nonexistent function 'new' in base 'GDScript'`，但文件语法没问题、编辑器里也不报错。
- **根因**：`global_script_class_cache.cfg` 没有更新，运行时不认识 `SpellA` 这个全局类名。
- **处理**：先 `godot --headless --import --path .` 再跑测试；把「新增 class_name 必先 import」写进环境铁律（E10）。
- **结果**：后续新增 `DuelSim`、`CharacterSelectPanel` 等全局类都按此流程，未再出现。
- **结论**：**headless 环境没有编辑器的自动导入**，任何「编辑器里好好的」都要怀疑缓存。

### C15 edit 的 old_string 被模板字符串吞了换行

- **场景**：用 `edit` 替换一段 GDScript，`old_string` 里含行尾续行反斜杠 `\`。
- **症状**：`old_string not found`，但肉眼逐字对比完全一致。
- **根因**：工具调用参数是 JS 模板字符串，行尾 `\` + 换行会被解释为「续行」，实际传给工具的内容已经少了换行。
- **处理**：含续行反斜杠的片段一律用 `String.raw` 包裹，或改成不含续行的锚点（选一段唯一的普通行）。
- **结果**：修复；同类问题在符卡 v4 实现里出现过两次。
- **结论**：**编辑工具的「文本」也要考虑传输层的转义**。锚点越短越安全，越靠近唯一标识越好。

### C16 截图拍不到效果：状态机下一帧就把它收走了

- **场景**：写 `tools/capture_fx_preview.gd` 截取刀光/粒子/心流环。
- **症状**：手动 `position` / `modulate` 摆好后截图，画面里效果位置不对或干脆没有。
- **根因**：`duel_view` 的 `_process` / `_physics_process` 每帧调用 `_update_*_fx()`，把手动设置覆盖掉；并行动画还会推进 `AnimationPlayer` 的轨道时间。
- **处理**：截图前 `view.set_process(false)`、`set_physics_process(false)`、`set("_flash", 0.0)`；动画要定格则 `state.get_track(0).call("set_track_time", 0.8333)` 再等 3 帧；截图脚本本身不参与 GUT。
- **结果**：截图可复现，三轮内收敛。
- **结论**：**「截图对不上」先怀疑驱动没停**，不要怀疑摆位算错。

### C17 看破的 6 帧优势被「临刀硬切」抹平

- **场景**：U05 给「看破」加 `hint_lead = 6`，让收束环提前 6f 出现。
- **症状**：实机完全看不出「提前」，看破像没生效。
- **根因**：`_update_charge_fx()` 在 `imminent`（临刀 8f 内）把整环硬切成纯金——提前出现的 6f 正好落在「会被硬切」的区间里，颜色差异被抹平。
- **处理**：抽出 `charge_color(progress, imminent, pulse)`，颜色沿 `smoothstep(0.12, 1.0, p)` 从近白到金，临刀只做 0.7 的 lerp 与 alpha 呼吸；给 `hint_lead` 一方额外一段环外冷白预读弧。
- **结果**：6f 优势在画面上可见；重拍截图确认。
- **结论**：**「实现了」和「看得见」是两件事**（E06）。任何「给了优势」的机制，都要检查它是否被后续的统一表现抹平。

### C18 .gitignore 不等于 Godot 不导入

- **场景**：把第三方素材包解压到 `temp_assets/`，并在 `.gitignore` 里排除。
- **症状**：Godot 仍然扫描并导入整个目录，`.godot/imported/` 里出现大量 `.ctex`，首次导入耗时暴涨。
- **根因**：`.gitignore` 只影响 git，不影响 Godot 的资源扫描。
- **处理**：在 `temp_assets/` 里放一个空的 `.gdignore`，Godot 就整目录跳过；验证方式是反查 `.godot/imported/` 里没有「未被选中文件」的 `.ctex`。
- **结果**：导入时间回落；入了 36 张筛选后的粒子贴图。
- **结论**：**引擎的忽略规则与版本控制的忽略规则是两套**（E10）。.gdignore 本身不入库，必须写进文档，否则换机器就复发。

### C19 assert_no_new_orphans 不能放 after_all

- **场景**：想在测试套件结束时统一断言「没有孤儿节点」。
- **症状**：报 `Nonexistent function 'size' in base 'Nil' addons/gut/test.gd:2085`。
- **根因**：GUT 的孤儿计数器只在当前测试结束时有效，`after_all` 阶段已经被清空（为 `Nil`）。
- **处理**：把 `assert_no_new_orphans()` 放进每个 `test_*` 的末尾；节点一律 `autofree` / `add_child_autofree`。
- **结果**：测试稳定，孤儿数不再随机波动。
- **结论**：**测试框架的钩子有生命周期**，断言要放在数据有效的阶段；错误堆栈里的 `addons/gut/test.gd:2085` 是判断依据。

### C20 契约化：从「33 个技能 0 加载」到「测试守卫」

- **场景**：10-21 审计发现项目引入 33 个 GDAS 技能但一次都没加载，`EventBus`/`UIManager`/`Codec` 三个插件零调用。
- **症状**：文档里写着「实现前先加载技能」，但实际会话的 `skill` 调用集中在 3 个会话、共 12 次；插件虽被 import，行为仍是项目自己实现的。
- **根因**：约定只存在于 `AGENTS.md` §9 的「背景说明」里，没有强制门、没有验收项、没有测试能发现违规。AI 在赶工时自然跳过「建议」。
- **处理**（四层）：
  1. `docs/dev-contract.md` 开工清单：读契约 → 首条回复列技能与插件 → 真加载；
  2. 任务 → 必载技能映射表（战斗判定 / 帧数据 / 动画 / 音频 / UI / 存档 / 测试 / 导出 / 性能）；
  3. 插件禁令 + `tests/unit/test_project_contract.gd` 扫描 `res://scripts/` 全部 `.gd`（剥离注释与字符串字面量，扫到的脚本数异常少也失败）；
  4. 验收 9 条 + 5 项登记豁免（限定文件）。
- **结果**：守卫测试可拦截 `Input.is_action_*`、`AudioStreamPlayer.new()`、`TranslationServer.`、`GUIDEMappingContext.new()`、`AudioServer.set_bus_volume_db` 等回归；插件从「接线」推进到「替换实现」（`Codec.record`/`AnyCodec`、`UIManager` 面板栈、`EventBus` 事件刷新、GUIDE 上下文资源化删约 300 行现搭代码）。
- **结论**：**没有测试的约定等于注释**（E08）。约束的落地形态是「文件 + 守卫 + 验收清单」，不是「一句话」。

## 8. 会话记录取数方法（可复用）

> 本项目 18 个会话、6415 次工具调用的统计，全部来自 DSH 会话文件。这一节给出可复现的取数方法，便于在别的项目上做同样的复盘。

### 8.1 数据在哪

- 目录：`C:\\Users\\<用户>\\.dsh\\sessions\\--E-godot-gamejam_1019--\\<会话 id>\\session.v4.jsonl.zstd`（目录名是「工作区绝对路径把 `:` 与 `\\` 换成 `-`」）。
- 每个会话一个文件；文件名即会话 id。文件是 zstd 压缩的 JSONL，每行一条事件。

### 8.2 关键坑：zstd 多帧

会话文件是**多次追加**写成的，因此包含许多独立的 zstd 帧。Node 的 `zlib.zstdDecompressSync()` 与 `createZstdDecompress()` 都**只解第一帧**，直接调用会得到被截断的前几条消息。

正确做法：按帧魔数 `28 B5 2F FD` 切分，逐帧解压后拼接：

```js
import fs from "node:fs";
import zlib from "node:zlib";

const buf = fs.readFileSync(file);
const MAGIC = Buffer.from([0x28, 0xb5, 0x2f, 0xfd]);
const starts = [];
for (let i = 0; i + 4 <= buf.length; i++) {
  if (buf.compare(MAGIC, 0, 4, i, i + 4) === 0) starts.push(i);
}
starts.push(buf.length);

let text = "";
for (let k = 0; k < starts.length - 1; k++) {
  const frame = buf.subarray(starts[k], starts[k + 1]);
  text += zlib.zstdDecompressSync(frame).toString("utf8");
}
const events = text.split("\n").filter(Boolean).map((l) => JSON.parse(l));
```

本项目实测 **2844 帧全部解压成功**，得到约 2100 万字符的 JSONL。

### 8.3 事件结构

每行形如 `{ "type": "...", "seq": n, "time": "...", "data": {...} }`。常用 `type`：

| type | 含义 | 取什么 |
|---|---|---|
| `session` / `title` | 会话元信息 | 标题、创建时间 |
| `turn` / `start` | 轮次边界 | 统计 turn 数 |
| `user` / `message` | 人类消息 | `data.content[]` 里的 `type: text` 块 |
| `assistant` / `message` | AI 回复 | `data.message.content[]`（reasoning / tool-call / text 块） |
| `tool/call` | 工具调用 | `data.name`、`data.arguments` |
| `tool/result` | 工具结果 | 输出、错误 |
| `todo` / `write` / `job` / `registered` / `workspace` / `changes` | 过程事件 | 辅助统计 |

### 8.4 统计口径（写文档时必须声明）

- **会话数**：`sessions` 目录下的子目录数（18）。
- **turn 数**：`type == turn` 的事件数（90）；一个 turn 可能包含多次工具调用。
- **人类消息数**：`type == user` 且正文字数 > 0 的消息（393）；排除系统注入。
- **工具调用数**：`type == tool/call` 的事件（6415）。
- **工具分布**：按 `data.name` 聚合；同一工具的不同子命令（如 `run_code` 内部调用的子工具）**不重复计数**。
- **案例引用**：人类反馈引用形如 `m01481`，这是 DSH 的消息编号，可在会话文件里对应到原始事件。

### 8.5 分析产物与清理

本项目把中间产物写到 `.tmp-analysis/`（`01-users.md` 全部人类消息、`02-assistant.md` 文本块、`03-tools.md` 工具分布、`summary.json` 汇总）。**这些是临时文件，不入库**；文档写完后删除目录，或加入 `.gitignore` 并在文档里注明。

**隐私**：只导出与本项目相关的文本；不把会话里的密钥、路径、个人信息写进公开文档。

## 9. 度量体系

> 只有能测的东西才能被优化。下表是本项目实际使用的指标、采集方式与读法，可直接迁移。

### 9.1 手感/数值指标

| 指标 | 定义 | 采集 | 本项目基准 | 读法 |
|---|---|---|---|---|
| 对方前摇 T | 出刀到判定的帧数 | `fighter_data.gd` | 28–30f（467–500ms） | 人类平均反应 0.2s = 12f，T 必须显著大于它 |
| 玩家前摇 | 同上 | `fighter_data.gd` | 14/11/17f | 低于 AI 读招 12–16f 会被「必架」 |
| 架窗 G | 可进入格挡的帧数 | `fighter_data.gd` | 18–22f | 可挡区间 `[T−G+1, T−2]` |
| 反应窗 | 人类能反应的下限 | 人类自述换算 | 6f（0.1s）极限 / 12f（0.2s）平均 | 小于 6f 视为不可反应 |
| 心流 | 资源值 | `duel_sim` | 0–100，自然恢复 +1/24f | 恢复速率要能支撑一次符卡 |
| 伤害 | 单次命中 | `fighter_data.gd` | 10/7/15（HP 30/30/40） | 3–4 次命中决胜 |

### 9.2 平衡指标

| 指标 | 定义 | 采集 | 判据 |
|---|---|---|---|
| 机器人胜率 | 三型机器人在矩阵上的胜率 | 探针 | NORMAL 档，均衡角色对快剑/重剑不出现 100% 或 0% 的双极 |
| 平均对局帧数 | 一局结束的帧数 | 探针 | 与设计目标（约 20–40 秒）比较 |
| 被架次数 | 玩家出刀被架次数 | 探针 | 过高 = 读招太强，过低 = 架防无意义 |
| 命中数 | 有效命中次数 | 探针 | 与 HP/伤害反推的结果一致 |

### 9.3 工程质量指标

| 指标 | 采集 | 本项目 | 用途 |
|---|---|---|---|
| GUT 用例 / 断言 / 脚本数 | gut_cmdln 输出 | 311 / 1270 / 37 | 数字变小 = 删了测试 |
| 契约守卫 | `test_project_contract.gd` | 绿 | 禁令未回归 |
| 冒烟 | `--quit-after 240` | 无 ERROR | 场景装配正常 |

### 9.4 度量陷阱

1. **GUT 通过 ≠ 玩起来对**（C01）：单元测试覆盖的是「已想到的路径」，探针覆盖的是「玩出来的路径」。
2. **指标测的不是同一件事**（C11）：探针测「能不能出招」，人类感知的是「按下去多久出刀」。
3. **个位数帧是噪声**（E01）：60Hz 下 ±3f 在人类时间阈限（10–20%）内，不要为它写平衡档。
4. **工具调用数不等于工作量**：`read` 1334 次里大量是重复读取；真正的产出看 `write`/`edit` 与最终文件。
