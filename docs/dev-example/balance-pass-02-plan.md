## 1. 反馈 1：反应窗口（P0，v2 重点改写）

### 1.1 先把「人的反应」换成毫秒

| 环节 | 典型耗时 | 说明 |
|---|---|---|
| 看见前兆、认出「这是斩」 | 200–250ms | 视觉简单反应；气环是从 COMMIT 首帧就开始画的，玩家有完整前摇可用 |
| 判断（是斩还是虚招 / 对方心流档位） | +50–100ms | 这一项是「剑术游戏」的灵魂，必须留够 |
| 按键 → 架子生效 | **33ms（2f）** | 1f 输入延迟 + 1f `guard_startup`，这是代码定死的开销 |
| **合计需求** | **≈300–350ms** | 也就是测试者说的「极限 0.3s」 |
| **设计目标（含容错）** | **450ms** | 给 100ms 余量；这是本次的门槛 |
| 容错上限 | 500ms | 再长就不像「快剑对决」了 |

### 1.2 窗口的几何（两条推论）

守方能挡住的条件是「按下 → 架子在斩落下时仍有效」，可挡区间恒为：

```
可挡按下区间 = [T - G + 1, T - 2]        T = 攻方前摇，G = 守方架窗（都是帧）
最晚能挡 = (T - 2) × 16.7ms              宽度 = G × 16.7ms
```

推论：

1. **上限只由 T 决定**（T-2 帧；那 2 帧就是输入延迟 + 起架）。前摇多长，玩家就有多少时间——**想放宽反应，只能加前摇**，加架窗没用。
2. **下限由 T-G 决定**。架窗越宽，越能容忍「按早了」。**架窗修的是「准度」，不是「反应」**。

这一条很重要，因为 v1 的方案其实搞反了主次：加架窗只让「按早了也挡得住」，真正卡住人的是前摇 300ms。

### 1.3 三档定档（毫秒视角）

| 档位 | 敌前摇 T | 玩家架窗 G（心流 SPREAD/CALM/FLOW） | 可挡按下区间 | 300–350ms 反应能挡？ | 450ms 余量 |
|---|---|---|---|---|---|
| **现状** | 300–333ms（18–20f） | 200/267/333ms（12/16/20f） | **16–266ms** | ✗ 必挨刀 | ✗ |
| v1 提案 | 367–400ms（22–24f） | 267/333/400ms（16/20/24f） | 50–333ms | ✓ | ✗（差 117ms） |
| **v2 提案（本次）** | **467–500ms（28–30f）** | **333/400/467ms（20/24/28f）** | **100–450ms** | ✓ 有 100ms 余量 | ✓ 刚好 |
| HARD（保留现状） | 317–333ms（19–20f） | 233/300/367ms（14/18/22f） | 50–300ms | 边缘 | ✗（有意为之） |

v2 的两个性质值得单独说：

- **上限 450ms 与心流档位无关**：心流只改下限（能多早按），不改「最晚能挡」。也就是说 **心流低不再等于「防不住」**——现状心流跌到 SPREAD 时架窗只剩 200ms，等于宣告「你已经死了，只是还没倒下」，这个死亡螺旋在 v2 里消失了。
- **下限 100ms**：手快的人不能抢按，得压到 100ms 之后再按。这是「按早了会空架（−8 心流 + 7–9f 收架）」这个既有惩罚的用武之地，也是 FLOW 档（467ms 架窗、下限 33ms）真正的价值。

### 1.4 顺带纠正一件事：单数帧的差异玩家感知不到

按你的判断（个位数帧数变化感知不到），量化一下：时间间隔的差别阈限大约 **10–20%**，在 300ms 尺度上就是 **30–60ms = 2–4 帧**。所以：

| 帧差 | 毫秒 | 感知 |
|---|---|---|
| 1–2f | 17–33ms | **噪声**，玩家分辨不出 |
| 3f | 50ms | 极难察觉 |
| 4–5f | 67–83ms | 勉强能说出「这刀快/慢」 |
| ≥6f | ≥100ms | **明确感知**，可以拿来做角色身份 |

现在的角色面板直接用掉了大量「噪声预算」：

| 参数 | A 均衡 | B 快剑 | C 重剑 | 差异 | 判定 |
|---|---|---|---|---|---|
| `base_commit` | 300ms | **283ms** | **350ms** | ±1–3f | **感知不到** |
| `guard_duration_base` | 200ms | **183ms** | **233ms** | ±1–3f | **感知不到** |
| `blocked_recovery` | 533ms | **467ms** | **600ms** | −4/+4f | 勉强 |
| `hit_damage` | 1 | 1 | 2 | ×2 | 强感知 |
| `stagger` | 0 | 0 | 200ms | +12f | 强感知 |

**结论 [提议]**：三把剑的 **架窗统一到 20f（333ms）**，把 ±1–3f 的「假差异」收掉；角色身份改由**伤害、破势硬直、被架硬直、消耗**这些「一眼能看见」的量承担。前摇如果要做角色差，必须 ≥5f（83ms）才有意义（比如重剑 400ms、快剑 283ms，差 117ms）。

> 这一条是纯设计取舍：如果你想保留「快剑前摇短一点」的设定，就得让它短 5f 以上，否则玩家只会觉得「都一样」。

### 1.5 窗口加大必须付的三个代价（不做就白调）

**代价 1：AI 的惩罚刀追不上了 → 必须给「反斩」一个更快的值**

AI 读招前摇 29f（483ms），而被架住的玩家硬直只有 28–36f（467–600ms）。惩罚刀要落在硬直里，前摇必须 ≤ 硬直：483ms 对 467ms 就是差一点——**B 的快剑会被架住之后还能反手架住**。所以「确定反」不能复用读招前摇，要单独取值：

```
反斩 commit = maxi(12f, base_commit - 10f)   ≈ 317ms（19f）
```

主题上也对：刀已经被架住了，攻方不需要再「构」，直接居合。**这条要写进设计文档的判定规则里**，属于新机制（§9 决策点 3）。

**代价 2：前摇越长，AI 越像活靶子**

在「斩 vs 构 = 无条件命中」这条规则下，AI 的 COMMIT 就是玩家白给的伤害窗口。前摇从 333ms 拉到 483ms，AI 待在可被砍的 COMMIT 里的时间长了 **45%**，连砍变强 [推算]。

补偿二选一（或都做）：

- **（推荐）AI「起构安全判断」**：玩家处于 `IDLE`（随时能出刀）时不起构，只在玩家 `GUARD / GUARD_REC / RECOVERY / SPELL` 时落构。3–4 个条件，改 `duel_ai.gd` 的 `_start_attack` 入口。副作用是 AI 看起来「真的会看人」，而且**可能本身就足以压死连砍**（[推算，待实测]）。
- 提高 AI 架率上限：`_guard_chance_now` 封顶 0.75 → 0.90。

**代价 3：前摇 +167ms 会让 AI 的 DPS 掉约 1/3**

所以 NORMAL 不能再用「决策节拍 +4f」去放慢 AI（v1 的方案），必须反过来压：

```
decision_interval -4f（-67ms）、post_hit_pause -20f（-333ms）
```

也就是 **「慢刀快心」**：每一刀都能读，但出手并不更少。这比「刀慢+出手也慢」更接近「居合的紧张感」——你永远有压力，但每次都有反应的时间。

## 2. 反馈 2：节奏与难度双档（P1，v2 修订）

### 2.1 节奏到底快在哪 [实测 + 推算]

| 指标 | 现状 | 说明 |
|---|---|---|
| 单场时长 | 5.2–6.5s（310–392f） | 连砍机器人 |
| AI 出手节拍 | 250–350ms 一拍 | 一拍就可能起一次构 |
| 玩家斩→构→斩周期 | 633ms（38f） | 双方都在「一秒两刀」的空间里 |
| 「看见到挨刀」 | **≤266ms 窗口** | 这才是「快」的真实来源：不是刀快，是**不给你看** |

**HP×10 不会放慢节奏**：血量与伤害同倍放大，对局长度实测 384f → 398f（+3%）。要慢，只能动前摇、AI 节拍、硬直回收。

> HARD 的前摇仍然是 300–333ms，即 **HARD 在物理上不可能靠反应防住**（§1.2）。这是有意的：HARD 是给背下节奏的人。但必须在设置里写清楚，别让人以为是自己的问题。

## 3. 反馈 3：角色平衡与「无脑连砍」（P0）

### 3.1 实测：谁强谁弱 [实测]

| 配置 | 机器人 | 均衡 A | 快剑 B | 重剑 C |
|---|---|---|---|---|
| 现状 | 连砍（每帧按攻击） | **100%** | 77% | **100%** |
| 现状 | 读招架 400ms | 53% 挡下 | 53% 挡下 | **0% 挡下（被打死）** |
| 现状 | 读招+罚 400ms | 33% | 44% | **100%** |
| 现状 | 读招+罚 500ms | 11% | 33% | **100%** |

三件事必须让审阅者看到：

1. **「无脑连砍」对三把剑都有效（77–100%）**，不是快剑专属。最强是**重剑**（4HP + 2 伤 + 200ms 破势，即使 500ms 反应也 100% 赢），最弱是**快剑**。
2. 快剑的 283ms 前摇没有变成先手优势：它更频繁进 COMMIT，而架窗最短（250ms）、被架硬直最短（467ms）——**攻防两头都薄**。
3. 「快剑无脑攻击能赢」在当前代码上成立，但换重剑只会更快赢。所以**平衡方向不是削快剑，是补快剑**；否则削完快剑，重剑的问题原样留下。

### 3.2 根因（两条，都在规则层）

- **根因 1：斩 vs 构 = 无条件命中。** 不管对方构到第几帧，斩落下就是命中。AI 大量时间在 COMMIT，于是**AI 的进攻欲望本身就是玩家的伤害来源**——越菜的 AI 越好打。
- **根因 2：被架几乎没有代价。** AI 惩罚分支：

  ```gdscript
  if foe.state == RECOVERY or GUARD_REC:
      if sim.frame >= _next_think_frame and rng.randf() < profile.counter_chance:
  ```

  既要等决策节拍（250–350ms 一拍），又要掷概率；而它自己的前摇已被拉到 367–433ms、玩家被架硬直只有 467–600ms → **惩罚刀经常来不及落下**。实测：连砍每场被挡 2.1 刀，只挨 0.9 刀（30 HP 里的 9 点）。

### 3.3 三条路径（按风险排序）

#### 路径 A（推荐，已实测）：AI「确定反」

```gdscript
if foe.state == RECOVERY or GUARD_REC:
    if sim.frame >= _attack_ready_frame and profile.counter_chance > 0.0:
        sim.press(side, ATTACK)   # 反斩前摇 base-10f，不走 _start_attack（避免排虚招）
    return
```

| 指标 | 现状 | 数值案+防守型 AI | **+ 确定反** |
|---|---|---|---|
| 连砍 A / B / C | 100 / 77 / 100% | 88 / 88 / 88% | **55 / 66 / 55%** |
| 连砍「被斩」伤害 | — | 8.9 / 10.0 / 13.3 | **15.6 / 13.3 / 20.0** |
| 读招+罚 200ms | — | 77 / 44 / 77% | 55 / 11 / 55% |
| 读招+罚 400ms | 33 / 44 / 100% | 88 / 88 / 77% | 77 / 88 / 55% |

代价：AI 变凶，**读招+罚 200ms 的快剑从 44% 掉到 11%**。所以 A 必须配合双档（NORMAL `counter_chance = 0.7`）+ 快剑补偿 + §1.5 的起构安全判断。

> 注意：上表实测用的是「前摇 +4f（367ms）」那档。v2 把前摇拉到 467–500ms 后，**这张表要重测**——AI 的构更长，连砍会更强（§1.5 代价 2）。批量实施第一步就是先跑一遍 v2 的探针矩阵。

#### 路径 B（需批准，未实测）：完美格挡 = 见切反击

完美格挡（架生效后 50–83ms 内被砍）时守方立即反击。优点是把「见切」从被动免伤变主动；风险是容易变成「对架游戏」，且要新开一个 ripped 状态、判定链加分支、测试面大。建议等 A + 双档上线看数据再说。

#### 路径 C（需批准，未实测）：连斩惩罚（间合）

出刀后 500ms 内再次出刀，本次前摇 +67ms（可叠到 +133ms），超过 500ms 不出刀则清零。效果：连砍周期 633ms → 767ms，前摇更长更易被读。实现成本：`DuelSim` 一个计数器 + `_enter_commit()` 一行。

### 3.4 HP×10 与伤害分布（你给的方案，采纳）

| 角色 | HP | 伤害 | 击杀所需刀数 | 备注 |
|---|---|---|---|---|
| 均衡 A | 30 | 10 | 3 | 基准 |
| 快剑 B | 30 | **7** | 5 | **最弱，必须补偿，见下** |
| 重剑 C | 40 | **15** | 3 | + 200ms 破势 |

**为什么快剑会被 7 伤打死**：B 的 DPS 优势只有「前摇 283 vs 333ms」+「空挥恢复 300 vs 333ms」≈ 1.25 倍，而要补 7/10 的伤害差需要 1.43 倍。差约 12%。所以 B 的定位应该是**防守反击型**（靠架和惩罚刀赢），补偿建议：

- `blocked_recovery 28 → 24f`（被架后 400ms 就能动，比 A 的 533ms 快 133ms）——**可感知**
- `whiff_recovery 18 → 16f`
- 前摇 16 → **15f（250ms）**：与 A 差 83ms，刚好跨过 §1.4 的感知门槛，也让「快剑」名实相符

**×10 的连带清单（不改就会当场坏掉）**——本方案最容易漏的部分：

| 位置 | 现值 | 必须改成 | 不改的后果 |
|---|---|---|---|
| `duel_ai.gd:53` | `me.hp <= 2` | `me.hp <= max_hp * 0.5` | 关底二阶段永不触发 |
| `duel_ai.gd:128` | `foe.hp <= 1 or me.hp <= 1` | 比例（`<= 0.34 * max_hp`） | 符卡永远在「不值得」时喷 |
| `spell_card.gd` | `amount` 2 / 3 / 3 | ×10（20 / 30 / 30） | 符卡伤害被普攻覆盖（`maxi(damage, amount)`） |
| `duel_view.gd:243` | `_draw_hp_pips` 画 `max_hp` 个 16px 方块 | 画 `max_hp/10` 个（或改分段血条） | 30 格 × 21px = 630px ×2 = 超出 1280 视口 |
| `duel_hud.gd` | `HP 3/3` 文本 | 无需改 | — |
| `run_state.gd:201` | `gold += 10 + player_hp * 2` | 按血量比例 | 每场白给 70 金，经济崩 |
| `run_state.gd:211` | `heal = 1`（心得 2） | 10（心得 20） | 回血等于没回 |
| `run_state.gd:33` | `player_hp: int = 3` | 30 | 首场 1 刀死 |
| `run_state.gd:97` | `data.max_hp += 1` | `+= 10` | HARD 加血失效 |
| 全部 `hp <= 0` 判定 | 0 | 不变 | — |

### 3.5 验收标准（毫秒化）

- 三把剑的「连砍机器人」胜率 **≤ 45%**，三把互差 ≤ 20%。
- 「读招+罚 200–400ms」不下滑到 30% 以下（不能让认真读招的玩家反而输）。
- 任意两个角色的平均对局时长差 ≤ 25%。
- **0.4s 反应的玩家对全部 5 场前摇的可挡率 ≥ 90%**（探针 bot d=24 帧）。

## 4. 反馈 4：更多角色 / 收服敌人（P2，预研，本轮不写代码）

### 4.1 现在的阻塞点

## 5. 反馈 5：开局待机不该涨心流（P0，最便宜）

### 5.1 实测 [实测]

纯 tick、不输入（stage 0/2/4 一致）：

| 帧 | 60 | 120 | 179 | 180 | 181 | 200 | 240 | 300 |
|---|---|---|---|---|---|---|---|---|
| 心流 | 42 | 45 | **47** | 47 | 47 | 46 | 44 | **41** |

开局 40 → 礼让 3 秒涨到 **47（+7）**，礼让一结束立刻开始「无输入惩罚」，5 秒后又跌回 41。玩家什么都没做，心流条先涨后跌——既误导教学，又让「心流稀缺」的设定失效。

### 5.2 原因

1. `duel_sim.gd:570` `_passive_flow()` 的自然恢复只判断 `frame - last_input_frame <= NO_INPUT_GRACE`（180f），**完全不看 `opening_lock_frames`**。
2. `last_input_frame` 初值 0，而礼让期恰好也是 180f → 礼让期被误判成「最近 3 秒有操作」。

### 5.3 方案

```gdscript
var unlocked := frame >= opening_lock_frames          # 礼让结束才允许自然恢复
var recently_active := unlocked and frame - last_input_frame <= NO_INPUT_GRACE
```

并在礼让结束那一帧把双方 `last_input_frame` 重置为当前帧，让「无输入惩罚」从真正能做事的时刻开始算。对称处理 P2。

- 副作用：开局少 7 心流，教学场第一刀前仍攒不到符卡（`spell_a` 消耗 30、`start_flow` 40），与现在一致。
- 测试：`tests/unit/test_duel_sim.gd` 里开局自然恢复相关断言；`balance-pass-01.md` §1 补一句「礼让期内不恢复」。

## 附：探针方法（可复现）

临时脚本放 `.tmp_probe/`（跑完已删，不入库），`extends SceneTree`，`--headless --path . -s .tmp_probe/probe.gd`。每场循环严格复刻 `duel_controller` 顺序：

```gdscript
sim.opening_lock_frames = 180
sim.p2.flow = 40
while not sim.finished and sim.frame < 1800:
    bot.step(sim)      # 机器人：连砍 / 读招架 / 读招+罚
    ai.tick(sim)       # DuelAi(P2, AiProfile.for_stage(stage), seed)
    sim.tick()
```

机器人只替代「手」，不替代「眼」：读招架 = 看到 COMMIT 后延迟 d 帧按一次架；读招+罚 = 再加「对方进 RECOVERY/GUARD_REC 立刻出刀」。这套东西以后可以直接长成 CI 里的平衡回归。
